# Experience: Xper Phase 0 bootstrap

- Status: accepted
- Date: 2026-10-01
- Approval source: the user's Xper Phase 0 specification.

## Decision

The concept name is **Experience**. Its internal Rails surface code is **xper**.
`Xper::App`, `Xper::Com`, and `Xper::Org` are independent boundaries. This is a parallel
bootstrap, with no authority cutover. **Base > Preference remains unchanged and remains the
existing authority during Phase 0**, including its database, JWT, cookies, synchronization,
routes, models, and UI.

| Edition | Public authority | Development private origin hostname |
| --- | --- | --- |
| app | umaxica.app | xper.app.localhost |
| com | umaxica.com | xper.com.localhost |
| org | umaxica.org | xper.org.localhost |

`PUBLIC_XPER_{SERVICE,CORPORATE,STAFF}_URL` and
`PRIVATE_XPER_{SERVICE,CORPORATE,STAFF}_URL` use scheme-less hostname values, matching the
Global ENV and route constraint contract. `ConfigValues::HostFamilyValues` converts public
values to validated origins. These values are distinct from the Tunnel service addresses
`http://xper.{app,com,org}.localhost:3000`.

Xper is ERB-based and owns Importmap/Propshaft application layouts. Its homepage is a static
landing page with no Inertia, React, actor hydration, preference controls, authentication,
or Preference/Experience credential issuance. The installed Inertia Rails gem globally
includes its controller integration into `ActionController::Base`; with forgery protection
enabled, its framework hook can emit CSRF and Rails session cookies even for ERB responses.
Xper adds no Inertia layout, page, share, or configuration, and does not remove that shared
security behavior. Tests distinguish those framework cookies from forbidden Preference and
Experience credentials. Both application and bare controller bases inherit directly from
`ActionController::Base`, declaring only FQDN availability, rate-limit support, and the
existing CSRF strategy. Application bases declare the existing 300/minute default web limit;
bare bases retain operational endpoint limits through their concerns. Roots use the application layout; machine and SEO endpoints use the
surface's independent bare base. Existing reviewed rendering/intake concerns are reused.

Phase 0 contains only homepage, health, revision, CSP report, temporary robots, and temporary
sitemap. It explicitly excludes Experience DB, JWT, cookies, API, refresh, synchronization,
ETag, CORS API, browser cache contract, Service Worker, manifest, and offline support.
The SEO placeholders retain a FIXME pending the final delivery mechanism. Their canonical
URLs come from public Xper configuration, including when reached through a private host.

Each Xper FQDN has its own registry slot. Availability flags are generated by the existing
registry contract. Development seed continues enabling registry flags; production remains
closed until an explicit operator action enables the three Xper flags. No fallback opens them.

## Routing exceptions and contract

`config/routes/xper.rb` uses resourceful routes and the pre-approved root exception:

```ruby
root to: "roots#index"
resource :health, only: :show, format: false
resource :revision, only: :show, format: false
resource :csp_violation_report, only: :create, path: "csp-violation-report"
resources :robots, only: :index, path: "robots.txt", format: false
resources :sitemaps, only: :index, path: "sitemap.xml", format: false
```

The permanent root infrastructure exception maps `GET /` to `RootsController#index`, with
`xper_app_root_path`, `xper_com_root_path`, and `xper_org_root_path`. Health and SEO paths
use their existing pre-approved infrastructure exceptions. The literal machine `.json` paths
and `/revision` reuse existing operational vocabulary, explicitly required by the specification.
Robots/sitemap delivery is temporary and will be replaced when SEO ownership is decided.
The risk is admitting the wrong host or pulling credential callbacks into apex requests;
route, registry, cookie, lifecycle, and isolation tests guard those boundaries.
Xper is explicitly exempt from the regional Preference contract and the actor/session common
controller pattern inventory, since Phase 0 owns neither kind of state. Bare/application
inheritance and brand-title inventories include Xper rather than importing that lifecycle.

All three editions expose the same matrix, resolved to their own `xper/<edition>` namespace:

| Method | Path | Controller/action suffix |
| --- | --- | --- |
| GET | / | roots#index |
| GET | /health | healths#show |
| GET | /health/liveness | health/livenesses#show |
| GET | /health/readiness | health/readinesses#show |
| GET | /health/startup | health/startups#show |
| GET | /revision | revisions#show |
| GET | /api/v0/health.json | api/v0/healths#show |
| GET | /api/v0/revision.json | api/v0/revisions#show |
| POST | /csp-violation-report | csp_violation_reports#create |
| GET | /robots.txt | robots#index |
| GET | /sitemap.xml | sitemaps#index |

Health uses `HealthCheckRendering` and the matching App/Com/Org profiles. Revision uses
`ApplicationRevisionRendering` and only `Rails.application.revision`. Machine JSON uses
`MachineJsonNegotiation`, retaining 406 and no-store behavior. CSP uses `CspViolationReport`,
retaining its scoped CSRF exception, bounded body, rate limit, structured intake, and 204.
The existing fixed CSP `report_uri` stays unchanged. No Xper OpenAPI document is created;
the app/com/org contracts cover its operational JSON paths, and route coverage includes xper.

## Warp static reconciliation

At the start of this work, routes, registry, Host Authorization, README, and public ENV already
used Warp (`www-jp.umaxica.*` / `warp.*.localhost`). The devcontainer frontend aliases alone
still used `wide.*.localhost`; these are old Wide aliases, not a separate active Side surface.
The intended Compose change replaces those three aliases with Warp and adds the three Xper
aliases. Persisted Warp availability flag names remain `fqdn_available_side_*`; those are
operational keys and are outside this rename. Other user work is preserved.

The agent environment mounts `.devcontainer` read-only. The exact narrow patch was prepared at
`tmp/xper-compose-aliases.patch`, and the user applied the host-side alias changes. Static YAML
validation confirms all six Xper/Warp aliases. During host editing the existing
`core-workers-vpc.internal` alias was temporarily removed. After reviewing the separate
Workers VPC contract, the user restored it. The final diff preserves that route and changes
only the requested Xper/Warp aliases. See the session evidence for the final state.

## Verification and activation

`test/integration/xper_bootstrap_test.rb` fixes the public/private route matrix, no-credential-cookie
homepage credential isolation, fail-closed availability, CSP boundaries, canonical SEO, and forbidden route contract.
`test/security/invariants/xper_phase_zero_invariant_test.rb` guards frontend and lifecycle isolation.
The existing cross-surface health, revision, CSP, FQDN, public-entrypoint, and OpenAPI inventories
cover Xper. Verification results belong in `evidence/`, including any blocked checks.

Phase 0 proves static configuration and Rails contracts; it does not assert network reachability.
The [Phase 1 Activation Gate](../docs/operations/xper-phase-one-activation-gate.md) must run after
devcontainer rebuild and before any Experience API implementation begins.
