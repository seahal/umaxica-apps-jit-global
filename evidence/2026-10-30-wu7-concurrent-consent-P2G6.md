# WU-7 concurrent consent choices

- HEAD: `336811e5072a93c0523e484f905082635b28f48f`; staged, unstaged and untracked changes affected the result.
- Added a nontransactional integration test that sends affirmative and negative consent requests with the same valid JWT and binding on separate connections. An independent PostgreSQL connection locks the original preference row; a separate observer confirms both requests are waiting before the lock is released. One request updates the original generation and the other creates a new generation after detecting the stale JWT. Both responses succeed, and each row's four consent flags, receipt revision, binding digest and JWT generation agree with its own request. The test removes its synthetic rows and audits.
- Before the change, the consent receipt tests passed: 13 runs, 111 assertions. The first new test run read a cached original receipt on the observing connection and failed; clearing that connection's query cache before inspecting the independently committed results fixed the observation. The combined concurrency and receipt selection passed: 14 runs, 131 assertions. After formatting and adjusting cleanup, the standalone concurrency test passed with 1 run and 20 assertions. RuboCop passed on the new test.
- This test observes one actual lock race without controlling which choice wins, and does not establish both predetermined commit orders or HTTP response delivery ordering. The JWT header example in `two.md` differs from the accepted RFC 9068 ADR and current code. The full-suite comparison and WU-7 completion remain unverified. No migration was run.
