# Global PostgreSQL Integrity Findings and Limits

This report uses the read-only development catalog captured in `tmp/postgresql-integrity-catalog.json` on 2026-09-24 against commit `2b027d5b38989d3068e4620262bfa6c6fde8df41` with uncommitted changes. The table-level matrix is `memos/postgresql-integrity-audit-matrix.md`; the version/table snapshot comparison is `memos/postgresql-integrity-drift-review.md`. The original F-01–F-21 report was unavailable, so no historic finding is inferred or marked resolved here.

## Coverage

- All 20 configured Global logical development databases were read through the `primary` PostgreSQL server. The live catalog contained 838 tables: 779 classified `OWNED` and 59 `THIRD_PARTY`. Of the owned tables, 709 have a model mapping or previously classified legacy identity, and 70 model-free tables were traced to creation or rename in the same logical database's application migrations. All 779 owned tables received catalog-level PK, sequence, FK, column, constraint, index, size, row-presence, and schema-version screening. Migration ownership does not prove current runtime use.
- All tables had a PK. No attached PK sequence had a narrower type than its PK. No live index had `indisvalid=false`. All 838 tables had SELECT privilege for the audit role, and none had RLS enabled. The exact FK child and parent column types matched for all live FKs; no parent relation was absent from the captured logical database. These are catalog observations, not workload or business-contract proofs.
- A bounded `EXISTS` check found 53 nonempty and 785 empty tables. The nonempty application tables were small lookup/event-class tables; all 101 tables carrying existing `NOT VALID` constraints were empty. PostgreSQL row estimates were often `-1`, so they are not used as row counts. This development environment cannot validate populated-data behavior or production-scale plans.

## Unverified contracts

The catalog establishes type, nullability, index and constraint structure, not the business meaning of each nullable or variable-length column. State-dependent requiredness, permissible state values, string character/byte limits, encrypted/plaintext size boundaries, JSON shapes, numeric precision appropriateness, index workload benefit, growth rate, and unused status remain unverified wherever a specific authoritative contract was not found. No arbitrary limit, enum, `NOT NULL`, or deletion is recommended from a column name, current empty rows, `idx_scan=0`, or a small development execution plan.

For tenfold, hundredfold, and thousandfold growth, additional storage and index-write work is a structural concern only. Those multipliers are scenarios, not measured growth or forecasts; workload measurements and representative row volumes are required before a performance conclusion. Production, staging, Regional, and external providers were not accessed.

## Verification disposition

The catalog inventory and structural screening cover all 779 owned development tables. The full business-semantic audit remains incomplete: authoritative state-dependent null rules, per-field limits, encrypted payload bounds, expected growth, query workload, and confirmed unused status were not established for every table. The shared development data is mostly empty and cannot stand in for populated environments. This is a concrete evidence gap, not a conclusion that the schema is sound or defective.

The approved ticket migrations passed synthetic SQL regression in the three migrated task databases and three fresh dump-reload task databases. Independent connection races passed for all three ticket databases, and exact catalog parity passed between each migrated database and its dump-reload peer. The related Rails test selection passed 121 runs and 420 assertions. The complete isolated Rails suite ran to completion but failed: 11,724 runs, 74,437 assertions, 26 failures, 15 errors, 8 skips. Its failures include authentication/controller contract assertions and missing lookup rows in test fixtures; their baseline status is unproven in a concurrently changing worktree. The ticket-specific result must not be represented as a green full suite.

The 203 existing `NOT VALID` constraints remain unvalidated. Their target tables were empty in the audited development databases, so the precheck was vacuous there. The separate approval register identifies the required decision before any formal validation or shared database rollout. No shared development/test database was changed, and production was not accessed.
