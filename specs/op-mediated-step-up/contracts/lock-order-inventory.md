## Required boundary

The accepted design requires the actor's Zenith principal lock before OP device, root and grant
locks; OP evidence locks remain held through the protected source commit. The accepted
`adr/root-login-establishment-boundary.md` records actor-before-ticket order. The OP authority stop
committer records device → root → grant order within OP. An inverse edge matters only when both
locks can be held simultaneously, including through an indirect call and when the second operation
will ultimately refuse.

## Reviewed non-inversions and related gaps

- `ClientSignUpFlow#with_cycle_lock` normally locks `Client` first and then its OP parent and flow
  when the in-memory `principal_id` is present (`app/models/client_sign_up_flow.rb:182–205`).
  `terminate_sign_up!` and `complete_sign_up!` in `ClientSecretPasskeyReservationIssuer` use that
  method. Cleanup now rolls back and retries the tested stale blank-to-bound instance actor-first;
  other blank-flow callers and callers already holding OP locks remain separate review items.
- `AppSignUpRegistrationCommitter` opens an OP transaction before a principal transaction, but locks
  `client` before `flow.lock_registration_parent!` and `flow.lock!`
  (`app/operations/app_sign_up_registration_committer.rb:20–26`). `ClientSecretClaimCommitter#call!`
  likewise opens the OP transaction before taking the actor lock but locks its OP rows only inside
  that lock (`app/operations/client_secret_claim_committer.rb:73–80`). Transaction nesting is not a
  reverse row-lock finding.
- `BaseStepUpAdmissionIssuer`, OIDC step-up authorization issuer/completion/cancellation, credential
  security transition, and the examined F1 credential/contact writers acquire their actor lock
  before their OP row locks. This does not prove O-10 commit ordering: for example, Q-1 ends its
  inner OP transaction before the outer actor transaction commits
  (`app/controllers/base/app/identity/mfa/challenges_controller.rb:51–71`). Principal-first locks
  alone do not satisfy the accepted commit boundary.
- `AvatarOwnerMembershipLockService` takes the actor and membership locks before the Avatar mutation
  and its evidence verification (`app/services/avatar_owner_membership_lock_service.rb:48–65`); the
  surrounding OP transaction in `AvatarAuthorityApiEndpoint#with_owner_step_up` opens before that
  but does not itself acquire an OP row lock
  (`app/controllers/concerns/avatar_authority_api_endpoint.rb:69–75`).
- `AdministrativeAccessLock`, `WithdrawalLifecycle`, `OrgOperatorLifecycleExecute`, and
  `SignRiskEnforcer` record an identity-stop event with the principal transaction and invoke
  `OpIdentityEventInvalidator` after commit. Those after-commit calls are not simultaneous principal
  → OP row locks, but their epoch checks and delayed-delivery races still need verification.
- `OidcAuthorizationTransactionPurger` locks OP authorization rows, then performs a Zenith `pluck`
  of Secret claim references (`app/operations/oidc_authorization_transaction_purger.rb:48–59`)
  without requesting a Zenith row lock. Its APP path also calls `AuthAdmissionBindingPurger`, which
  locks Auth parent/binding/session rows and may delete terminal signup flows using `delete_all`;
  the inspected path does not acquire a Client/Operator row lock or invoke a principal-locking
  callback. The adjacent resolution and flow locks are OP-local. No OP-to-principal reverse edge was
  found in these direct purge paths; indirect callers outside the job entry and unrelated callbacks
  remain unverified.
- The IAM owner API now passes the evidence yielded by `require_owner_step_up` into
  `OrgIamOwnerMutation`. `OrgIamPrincipalCommit` locks actor and target Operators in deterministic
  ID order, then OP evidence rows; it rechecks evidence and policy, commits the Zenith mutation and
  operation outcome while the read-only OP transaction remains open, and refuses enclosing
  transactions. `test/integration/base_org_iam_owner_api_test.rb` exercises the public API's
  missing-proof refusal, grant, exact replay, same-ID input conflict and revoke audit result. The
  Support owner API still discards evidence yielded by `with_owner_step_up`; its existing writer
  stops APP roots in separate commits, so partial and unknown outcomes cannot be treated as a
  rolled-back transaction. The candidate Support design is
  `o10-support-session-revocation-design.md`; it is not active. Do not activate Support until its
  source outcome, partial delivery and audit recovery contract is reviewed and implemented. The
  complete reverse-lock inventory and independent-connection tests remain open.

## Passkey registration commit boundary

Source inspection on 2026-11-04 confirms a remaining O-10 violation in
`IdentityPasskeyRegistrationFinalCommitter`: the Zenith actor lock is acquired first, then the OP
transaction locks device/root and registration rows; the operation consumes the OP
candidate/ticket/ceremony before `PasskeyRegistrationOperation` creates the Zenith credential and
outbox. Because the principal transaction is nested in the actor transaction, OP commits before
Zenith. The current APP and ORG commit-order tests assert this order. The source outbox records
`operation_ref = transaction_id`, but `operation_ref` is not unique and the final committer does not
consult it to reconcile a source commit.

The O-10 contract requires the Zenith write to commit while OP authority locks remain held and keeps
the authorization OP transaction read-only. Moving OP completion to a second transaction creates a
post-source expiry/revocation interval: `AuthCeremonySession#complete!` rejects an expired ceremony.
Completing it before the Zenith write would instead make a source rollback leave a completed
ceremony. No implementation change was made because the safe post-source state transition, durable
receipt identity and replay outcome need a resolved contract. See `six.md`. The inventory remains
incomplete.

## Support session-revocation trace — 2026-11-05

`Base::Org::Api::V0::Support::AccountsController#revoke` authenticates the Base ORG caller and
checks the Support policy before calling `with_owner_step_up`
(`app/controllers/base/org/api/v0/support/accounts_controller.rb:80–84`). The wrapper resolves
evidence before opening an `OperatorToken` transaction, then yields the evidence
(`app/controllers/concerns/avatar_authority_api_endpoint.rb:69–75`). That transaction does not
itself lock the Operator or the evidence rows, and the controller block discards the yielded value.

`revoke_sessions` writes the Chronicle intent before entering `AccountSessionRevocation.purge!`
(`app/controllers/base/org/api/v0/support/accounts_controller.rb:141–155`;
`app/controllers/concerns/org_administrative_audit.rb:40–55`). The purge snapshots the target
Client's currently usable roots from the APP OP store, then calls
`AuthenticationLogoutCurrentSession` once per root
(`app/services/account_session_revocation.rb:49–67`). Each call opens an APP OP writer transaction
for the `ClientToken` owner
(`app/controllers/concerns/authentication_logout_current_session.rb:33–42,120–135`;
`app/models/client_token.rb:89`) and delegates to `OpAuthorityStopCommitter`; the stop primitive
locks Device Session → root → grants and writes its durable back-channel participants
(`app/controllers/concerns/authentication_logout_current_session.rb:215–225`;
`app/operations/op_authority_stop_committer.rb:126–142,209–245,263–275`). Each root stop commits
independently. Only after the loop does the purge write `AccountAccessEvent` in Chronicle
(`app/services/account_session_revocation.rb:108–128`); the administrative result is a further
Chronicle write.

This trace establishes no OP → Zenith reverse row-lock edge because the current path takes no
Operator or Client Zenith row lock. It also does not satisfy O-10's actor-first source-commit
contract: the evidence is neither passed to the writer nor rechecked under an actor lock, the target
stop has no operation-specific Client Zenith receipt, and a failure after one or more APP OP commits
can leave partial revocation without an `AccountAccessEvent`. The outer ORG OP transaction remains
open across these independent commits but holds no demonstrated source lock. Do not treat that
transaction nesting as atomicity or as proof of a safe lock order. The reviewed
`o10-support-session-revocation-design.md` remains inactive; source receipt, partial-delivery
recovery, audit outcome, and independent-connection ordering still need an accepted contract and
verification.
