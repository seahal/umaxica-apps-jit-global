# Remaining association index review

57 individual MissingIndex reports remain after the three inverse-key corrections. No index has been
added or removed. Index definitions below are the observed real catalog, not just schema dump
annotations. Predicate, uniqueness, column order and all other properties remain in the full
`index-review.md` and raw inventories.

- 48 reports: four reverse-reference columns on each of twelve RP cells. Initial schema explicitly
  disables reference indexes and creates identity/expiry/public-ID indexes instead; none leads with
  these FK columns. Parent associations really issue FK equality/existence queries. D4 proposes four
  nonunique concurrent indexes on rp_base_app only, pending local schema approval.
- Three reference-state transaction associations: state_id has no leading-column index. Existing
  partial indexes cover waiting/open workflows through other leading columns, not arbitrary state
  catalog traversal. Production row distributions and value selectivity are unknown; no performance
  conclusion from empty local tables.
- Three logout participant outbox associations: logout_flow_participant_id has no leading-column
  index; event-id uniqueness and due-work indexing serve other access paths. Retention/deletion
  semantics and parent lookup workload need focused review.
- Three core bridge has_one associations: the FK is already the leading column of a composite
  UNIQUE(actor_id,rp_client_id). These are a cardinality requirement from the checker, not absence
  of a search index. Do not add UNIQUE(actor_id) until multi-client identity contracts and data are
  proven compatible. Tightening uniqueness or changing association cardinality is a separate
  semantic decision.

Nonunique index additions preserve duplicates, NULL and constraint enforcement but consume storage,
WAL and update work. Rehearse builds and rollback, inspect invalid concurrent-build leftovers and
actual query plans before migration closure. No synthetic/empty-table EXPLAIN is production proof.
