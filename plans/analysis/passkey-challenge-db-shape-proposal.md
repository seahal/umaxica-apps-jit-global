# Durable remaining WebAuthn challenges

Status: proposed; requires explicit data-shape approval. This is the remaining shared challenge
retirement work in R06, not a substitute for Base-only registration finalization.

## Before

`Webauthn::ChallengeStore` stores up to five entries in the Auth Rails session cookie:

```json
{"passkey_challenges":{"reference":{"challenge":"public challenge","purpose":"authentication","surface":"app","rp_id":"auth host","origin":"https://auth host","actor_global_key":null,"expires_at":123}}}
```

Consumption removes a cookie entry. An older copy of the cookie can restore that entry. The current
DB-backed ordinary step-up path already avoids this store; primary sign-in, ORG Emergency,
APP/COM sign-in MFA, settings registration and signup checkpoint registration still use it.

## After

Add nullable challenge columns to the existing actor-specific `*_auth_ceremony_sessions` tables:

```text
webauthn_challenge_ref:string
webauthn_challenge:string
webauthn_challenge_purpose:string
webauthn_challenge_stage:string
webauthn_challenge_actor_ref:string
webauthn_challenge_rp_id:string
webauthn_challenge_origin:string
webauthn_challenge_expires_at:datetime
webauthn_challenge_consumed_at:datetime
```

The admitted continuity row already identifies the exact sign-in, signup, authorization or
registration permission transaction. No generic flow table or duplicate transaction success flag
is introduced. Each continuity row holds at most one current challenge. Replacing it by an
authorized POST invalidates its previous reference; consuming it never extends its deadline.
The reference is generated by the server and has a unique partial index when present. Challenge
bytes come from WebAuthn options, are public protocol data, and are not an authenticator private key.

Purpose retains the existing `authentication`, `emergency_sign_in`, and `registration` namespaces.
The independent stage enum is `primary`, `mfa`, or `registration`; server controller/flow state
supplies it, never a request parameter. Purpose/stage constraints permit authentication in
primary/MFA, Emergency in primary, and registration in registration. Ordinary step-up continues
using its existing approved transaction/session challenge fields.

The existing surface-specific RP configuration supplies RP ID and origin snapshots. The resolved
actor supplies its nonsecret public reference; anonymous APP/COM primary discovery may omit it.
Actor-known MFA, ORG Normal/Emergency and registration require it. Named columns preserve
independent validation and SQL constraints; a positional tuple is unsuitable for these optional,
independently queried properties. Expiry is the earlier of the existing ten-minute challenge limit
and the fixed underlying ceremony/transaction deadline. Issue and consume use writer time and
row locks. A mismatch spends the challenge before reporting failure, without rolling consumption
back when the verifier rejects. Flow stage, purpose, surface, actor and continuity are rechecked.

DB checks require all challenge properties together except the conditionally optional actor and
the initially absent consumed timestamp. They constrain stage/purpose combinations and ensure
consumption does not predate issue-related row state. Existing rows with no challenge receive no
new authority. Old CookieStore challenges are ended; the replacement has no Cookie/JWT fallback.
Session rotation, cancellation, completion, logout and credential-security transitions terminate
the owning row or its authority, so a stale challenge cannot survive those events. Existing
ceremony retention removes short-lived rows; deletion cannot reconstruct a spent reference.

Migration is additive on the three ticket databases. It includes no destructive rebuild, shared
database operation, deployment or bulk authority transfer. Rollback must end new ceremonies
before removing their fields, and must not re-enable Cookie-only consumption.

Primary options and verification response shapes remain unchanged. The APP primary Email JSON
decision remains held. MFA currently issues from GET; its display will become non-consuming,
with challenge issuance through POST. Any required new MFA props/endpoint contract will be
presented separately before its implementation. Settings registration also remains subject to
the existing Base candidate proposal and approval.

Acceptance requires stale-cookie replay, cross-browser/continuity, wrong stage/purpose/actor/RP/
origin, parallel consume, exact expiry boundaries, unavailable writer, terminal parent, rotation,
signup checkpoint and shared primary/MFA/Emergency regression tests. Browser checks remain user-owned.
