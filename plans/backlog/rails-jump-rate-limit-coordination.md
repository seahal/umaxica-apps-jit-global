# Rails-side consideration of Jump rate limiting

Date: 2026-10-11
Status: **PROPOSAL / BACKLOG / TBC — not an accepted ADR or implementation authorization**
Proposed repository location: `plans/backlog/rails-jump-rate-limit-coordination.md` in `seahal/umaxica-apps-jit-global`

## Context

UMAXICA Jump is an independent, short-lived, stateless, signed-navigation trust boundary. Its current Cloudflare Workers Rate Limiting binding rejects requests that exceed its configured limit with HTTP 429. A returned 429 normally stops a browser navigation at Jump. The Rails issuer does not receive that browser response as a server-side callback.

The signed inbound Jump RT has a maximum structural lifetime of 30 seconds and uses `rpl: reuse`. A user-initiated reload can succeed only if the limiting condition has ended and the original token remains valid. Otherwise the request stays refused; an expired RT requires starting a new authorized navigation at the originating service.

Jump's normal rate-limit rejection and failure of the rate-limit provider/binding are **separate** situations with separate, currently deferred policy questions.

## Recorded design direction

1. **Future Rails-side consideration is required.** Rails must eventually assess how to avoid unnecessary or excessive Jump requests, including repeated issuance, duplicate browser navigation, accidental loops, speculative loading, and load generated by its own workflows. This is a required *review topic*, not approval of a particular counter, quota, scheduling mechanism, or implementation.
2. **Do not assign rate-limit compensation to the trust boundary.** A Jump 429 terminates the attempted navigation. Jump must not automatically wait, queue, issue a replacement RT, extend token lifetime, bypass validation, or redirect to an unverified fallback merely to recover availability.
3. **Do not add automatic Rails compensation for Jump 429.** Rails must not attempt to intercept a browser-facing Jump 429, replay or renew the rejected RT automatically, bypass Jump with a direct cross-origin redirect, or recreate authentication/authorization state without its normal validated entry process.
4. **Retain ordinary user-initiated recovery.** A manual reload of the same Jump URL may succeed only while its original RT is still valid and the limit is no longer exceeded; there is no success guarantee. After expiry, the user returns to the originating service and starts a fresh normal request.
5. **Preserve separate enforcement.** Any future Rails-side limiting is an upstream load/abuse control, not a substitute for Jump's independently enforced limit, cryptographic verification, directed-edge policy, or receiver-owned authentication/CSRF/transaction controls.

## Deferred design questions (TBC)

- Whether Rails should implement a new admission limit before RT issuance, reuse an existing Rails-native/Valkey control, or simply eliminate duplicated issuance/navigation first.
- Appropriate limits, partitions, failure responses, fairness implications, and handling of a Rails rate-limit-store outage; no numerical policy is accepted here.
- Whether any form of waiting, request pacing, or client notification is warranted; automatic waiting inside Jump is not part of the current proposal.
- The Cloudflare Rate Limiting binding exception policy (logged fail-open versus fail-closed) and the independent treatment of `/health*`, `/.well-known/jwks.json`, and public assets. These are Hono-side decisions, not a Rails-only change.
- How to test and monitor legitimate 429 rates, double submission, Inertia/Turbo navigations, expiry, manual retry, and route or issuer changes without exposing RTs or sensitive URLs in logs.

## Investigation required before promotion

- Inventory actual Rails-to-Jump entry paths, explicit and implicit RT issuance, redirect chains, browser navigation types, loops, and duplicate requests, including `app`, `com`, and `org` surfaces.
- Establish measured legitimate volume, false-positive risk, and the effect of Jump's per-location limiter behavior without assuming it is a globally exact counter.
- Compare alternatives under the fixed Jump 30-second lifetime; maintain exact `iss`, `aud`, `rpl`, signature, URL, and receiver security requirements.
- Evaluate proposed Rails-side changes independently from a future Hono rate-limit policy review.
- Require focused regression tests for normal flow, 429, valid-token manual reload, expired-token rejection, and the fresh origin-service entry path; run end-to-end checks before adoption.

## Scope and release boundary

This document records a **mandatory future design review**, not a commitment to change Rails or Hono now. The policy and implementation remain TBC, are outside the current Jump 0.4.0 feature cycle, and are **not by themselves a new 0.4.0 release blocker**. Existing known risks must still be disclosed at release review. Only a later accepted decision and separately authorized implementation may change runtime behavior.
